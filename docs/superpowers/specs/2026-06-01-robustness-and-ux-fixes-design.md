# 鲁棒性与体验修复设计（盲测前）

- 日期：2026-06-01
- 背景：盲测标的「淮能电力凤台」（单 docx）跑出覆盖率 0/0/0、大纲标题重复 3 次，暴露理解链路的脆弱假设。
- 最高原则：**不过拟合，做普适性**。所有修法针对"如何鲁棒处理结构各异的真实标书"，绝不为某个具体文件写特判。

---

## 1. 问题与根因（已确认）

对比**能跑通**的北京院标的（451 条要求）与**失败**的淮能标的（0 条），根因是结构性的、非淮能独有：

### 1.1 覆盖率 0/0/0（要求抽取为空）—— 最核心
链路 `locate → _gather_span → extract_requirements` 在三处依赖脆弱假设：
- **locate 漏定位**：淮能原文行 270-353 实有"技术规范/技术参数"，但 `locate` 返回 `tech_spec_sections: []`。它只看「章节标题 + 200 字摘要」判断，内容标题不显眼（藏在"第二卷"、或表格里）就漏。
- **取文丢表格内容**：`_docx_to_md`（[extract.py:57-60](outline_extraction/parsing/extract.py#L57)）把**所有表格统一追加到文档末尾**，脱离原始章节位置。评分表/技术参数表多为表格，于是它们与所属章节失联——`_gather_span` 取章节正文时根本拿不到表格内容。淮能末尾一堆 `| | |` 空表格即此证据。
- **段落正文被误判为标题**：`segment` 正则 `^\d+\.\s`（[segment.py:13](outline_extraction/understanding/segment.py#L13)）把"1. 投标价格…"这类正文句当成 L1 标题，层级被压平，正文错位（淮能 section 91-98 全是 content=0 的"标题"）。

结果：喂给 `extract_requirements` 的文本是空的（"第二章 评标办法"只剩 19 字引子）→ 抽 0 条 → 覆盖率 0/0/0。

### 1.2 标题重复 3 次
淮能 docx 里"投标文件格式"内容**多处出现**（须知里的简表、第四章详细格式、签署说明里的罗列）。`locate` 把 7 个 section 都当 `bid_format`，`merge` **不去重语义重复的骨架节点** → 同一"商务投标文件"平铺 3 份。

### 1.3 体验缺口
- 前端样式朴素，不适合客户演示。
- 前端上传只支持单文件（`<input>` 无 `multiple`，`/api/upload` 只存一个），无法上传多文件包。

---

## 2. 范围

本期做 **A 方案（修主链路）+ 体验增强**，共 4 项。**B 兜底（全文扫描补漏）不在本期** —— 作为"盲测验证后按需启用"的预案（见 §7）。

| # | 问题 | 修法 |
|---|---|---|
| 1 | 要求抽取 0/0 | segment 信任原生标题 + 表格就地保留 + locate 更鲁棒 |
| 2 | 标题重复 | merge 语义去重重复骨架 |
| 3 | 前端美化 | 重做视觉（Alpine+Tailwind，中性灰+单一品牌色） |
| 4 | 多文件上传 | 前端多选 + 后端合并（管线逻辑不变） |

---

## 3. 修复 #1：要求抽取鲁棒化（核心）

三个子修复，从源头到下游：

### 3.1 表格就地保留（parsing/extract.py）
**问题**：表格被统一甩到文末，与章节失联。
**修法**：改 `_docx_to_md`，**按文档流顺序遍历 body**（段落与表格交错出现的真实顺序），表格在其原始位置转成 Markdown 表格，而非最后统一追加。
- 用 `python-docx` 的 body 元素迭代（遍历 `document.element.body` 的子元素，区分 `<w:p>` 段落与 `<w:tbl>` 表格），保持原始顺序。
- 这样评分表、技术参数表就留在它们所属的章节标题之下，`_gather_span` 能取到。
- 普适性：对所有 docx 生效，不针对特定表格。

### 3.2 segment 优先信任原生标题（understanding/segment.py）
**问题**：正则把正文误判为标题，压乱层级。
**修法**：分两档，**有原生 Markdown 标题就信任它**：
- 文档**含 `#` 标题**（docx 由 Heading 样式转来）→ **只认 `#` 作为标题来源**，`#` 数量即层级；其余行一律正文。**不再用 `^\d+\.`/`一、`/`（一）` 等正则把正文升级为标题**。
- 文档**无任何 `#` 标题**（如 textutil 抽的 .doc 纯文本）→ 退回现有正则模式兜底（保留 `第X章`/`一、`/`1.1` 等，仍是当前行为）。
- 判定方式：扫描全文，若存在以 `#` 开头的行，即走"信任原生标题"档。
- 普适性：规整 Word 文件（多数正规招标文件）层级会非常准；无样式文件不退化。

### 3.3 locate 更鲁棒（llm/prompts/locate.txt + understanding/locate.py）
**问题**：只看标题+短摘要，漏定位深层/表格里的技术评分内容。
**修法**（两点，均不写死特定文件）：
- **加长喂给 locate 的摘要**：摘要从 200 字增到更能反映内容的长度（如 400-500 字），让 LLM 看到章节里是否含评分项/技术参数/表格特征。
- **prompt 强化**：明确提示——技术规范/评分表/商务条款**常以表格形式出现或藏在"技术部分/第二卷"等卷册下**；标题不含关键词时应依据**正文内容特征**（出现"得分""分值""≥/≤ 参数""偏离表""响应"等）判断。仍强调依据语义、不依赖固定关键词或编号。
- 取文侧：`_gather_span` 逻辑不变（3.1+3.2 修好后它自然能取到完整章节含表格）。

> 设计取舍：本期**不改"先定位再抽取"的两阶段架构**（保持分层清晰），只让两阶段各自更鲁棒。若盲测显示仍有标的抽空，再启用 §7 的 B 兜底。

## 4. 修复 #2：merge 语义去重（alignment/merge.py + prompts/merge.txt）

**问题**：同一投标文件结构多处出现，骨架平铺多份。
**修法**：在 merge 的 prompt 里增加去重指令——
- 当骨架树中存在**多个语义等价的章节**（如多处"商务投标文件/投标函"），应**合并为一个节点**，保留最完整的一份，其余的来源/ref_ids 归并到该节点；不要平铺重复标题。
- 合并依据语义判同（与现有"质量管理体系认证≈ISO9001"同理）。
- 普适性：靠语义判重，不针对"商务投标文件"这个具体词。

> 注：骨架去重也可在 `extract_skeleton` 阶段做，但放在 merge 更合理——merge 本就是全局归并的环节，已有树的全局视野。

## 5. 修复 #3：前端美化（web/index.html + app.js）

保持 **Alpine + Tailwind（CDN，无构建）**，重做视觉，面向客户演示：
- **风格：简约、大气、Apple 风**。极简、留白充足、克制——**不要复杂配色**。
  - 配色：白/近白底 + 多档中性灰（文字、边框、次要信息）为主，**仅一个克制的强调色**（用于按钮、当前阶段、关键状态），其余尽量黑白灰。
  - 字体：优先系统字体栈（`-apple-system, "SF Pro", "Helvetica Neue"...`），靠字重/字号建立层级（大标题中粗、正文常规、次要信息浅灰）。
  - 质感：大圆角、极轻阴影或仅细边框分隔、充足留白、对齐严谨；避免重边框、重阴影、多色块。
  - 状态色克制：完成/警示等用最小必要的色彩点缀（细微绿/琥珀），不大面积上色。
- **布局**：顶部标题区；上传卡片（拖拽 + 多选）；处理流程竖向时间线（保留并按 Apple 风重做）；覆盖率卡片（评分/技术/商务三栏，状态色克制）；大纲树卡片（来源徽章低饱和、AI 建议极浅背景、层级缩进清晰）；导出区。
- 不改数据流，纯展示层。完成后用 **Chrome DevTools 截图验证**实际渲染（桌面+窄屏），遵循全局 UI 规范。

## 6. 修复 #4：多文件上传（web + api/main.py）

**机制**：管线本就支持"目录下多文件全部摊平、统一理解、合并成一棵大纲"（`collect_files` 遍历目录）。只需打通上传端：
- **前端**：`<input type="file" multiple>` 支持一次选多个文件；显示已选文件列表。
- **后端 `/api/upload`**：接收多个文件，全部存到同一个 `runs/<run_id>/input/` 目录；`UPLOAD_STORE[run_id]` 指向该 **input 目录**（而非单文件）。
- **管线调用**：`run_pipeline` 传入 input 目录，`collect_files` 遍历得到全部文件 → 现有流程不变。
- 单文件上传仍兼容（目录里就一个文件）。
- 普适性：多文件包与单文件走同一条合并处理路径。

## 8. 验证

1. **单测**：相关模块（extract/segment/merge/api）单测全绿；新增覆盖"表格就地保留""有#标题时不被正则误判""多文件上传存目录"的用例。
2. **回归**：重跑北京院标的（451 条），确认 A 的改动**不破坏已能跑通的标的**（覆盖率仍合理、不回退）。
3. **盲测**：重跑淮能 + 赞比亚，看：
   - 覆盖率是否不再 0/0/0（要求被抽到）；
   - 标题重复是否消除；
   - 若仍抽空，记录现象 → 触发 §7 的 B 预案评估（不在本期改）。
4. **前端**：Chrome DevTools 截图验证美化后渲染 + 多文件上传交互（桌面+窄屏）。
5. **诚实记录**：盲测如仍有缺口，如实呈现（覆盖率诚实是 Demo 卖点），不为通过而写特判。
